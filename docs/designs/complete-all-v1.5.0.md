## P0 — Desktop Compatibility: ทดสอบไม่ได้บนเครื่องนี้

**หลักฐานที่วัดได้**

```
ls engine/node_modules/ | grep -ci "desktop\|electron"   → 0
ls -d engine/node_modules/@deepseek-ai/*desktop*         → ไม่พบ
```

เครื่องนี้มีแต่เอนจินสำหรับ DSH บน Android ไม่มี DSH Desktop และไม่มี Electron
จึง **ติดตั้งและเปิดใช้งาน DSH Desktop จริงไม่ได้** ทุกข้อใน P0 ที่ต้องทดสอบจริง
(ทดสอบติดตั้ง, เปลี่ยนภาษา, fallback) จึงทำไม่ได้

**สิ่งที่ตรวจจากซอร์สได้ (และตรวจแล้ว)**

- `dsh-client-locale/lib/client.js` อ้าง `__DSH_LOCALE__` 1 จุด ใช้เป็นสะพานอ่าน
  ค่า `languages` กับ `preference` จากโฮสต์ (`parseLocaleBootstrap`)
- ถ้าไม่มีสะพาน (`bridge === undefined`) เอนจินยังทำงานได้ปกติ โดยใช้
  `resolveInitialLocale` → `detectBrowserLocale` → ตกเป็น `en`
- ปลั๊กอินนี้ไม่แตะสะพานเลย ใช้แค่ `addLanguage` / `register` / `setLocale`
  จึงไม่ผูกกับ Desktop เป็นพิเศษ

**สรุป P0**: โค้ดไม่ผูกกับ Web จน Desktop พัง แต่ **ยังไม่มีการทดสอบจริงบน Desktop
จึงต้องคงสถานะเดิมใน README คือ "ยังไม่ได้ทดสอบติดตั้งจริง" ห้ามอ้างว่ารองรับ**

## P1 — Human Translation QA (178 รายการ)

`TRANSLATION_REVIEW.md` มี 178 รายการ เกิดจาก heuristic (คำที่ปรากฏครั้งเดียว
และมีสระ/วรรณยุกต์) ไม่ได้แปลว่าผิด ต้องอ่านทีละรายการในบริบท

**สถานะ**: ยังไม่ได้ตรวจด้วยตา ต้องทำเป็นรอบ ๆ และบันทึกว่าแต่ละรายการ
`ถูกอยู่แล้ว / แก้แล้ว / ยังไม่ตรวจ` ลง `TRANSLATION_STATUS.md`

**ข้อผิดพลาดของเอกสารเดิมที่พบ**: หัวไฟล์ `TRANSLATION_REVIEW.md` บอกว่า
"ดึงจาก `lib/client.js` ณ เวลาที่สร้าง" แต่ค่าข้างในบางรายการอ้างข้อความที่
แก้ไปแล้ว (เช่นคีย์ที่ผมแก้คำเพี้ยน 22 จุด) จึงต้องรัน
`node tools/build-translation-review.mjs` ใหม่ก่อนเริ่มตรวจ

## P2 — Automated UI Testing: ทำได้บางส่วน

**สิ่งที่ทำได้บนเครื่องนี้**

- มีเครื่องมือ `ui` ที่ควบคุม WebView ของแอปนี้ได้จริง (`dump`, `tap`, `text`, `where`)
  ใช้ตรวจได้ว่าเปิดหน้าไหนแล้วข้อความไทยขึ้นครบไหม
- ทดสอบ Locale Switching ได้จริงโดยเปลี่ยนภาษาแล้วอ่านข้อความบนจอ

**สิ่งที่ทำไม่ได้**

- Desktop ไม่มีให้ทดสอบ
- ไม่มีเบราว์เซอร์แยกให้รัน Playwright/Selenium และโปรเจกต์ห้ามเพิ่ม dependency
- "ตรวจข้อความอังกฤษที่ยังไม่แปลทุกจุด" ทำอัตโนมัติครบไม่ได้ เพราะไม่มีต้นฉบับ
  อังกฤษครบทุกคีย์ในเครื่อง (คีย์ส่วนใหญ่มีแต่ค่าไทยใน `thDicts`)

**ข้อจำกัดที่ต้องยอมรับ**: การตรวจ UI อัตโนมัติจะครอบคลุมได้เฉพาะหน้าจอที่
เครื่องมือ `ui` เปิดถึง ไม่ใช่ทั้ง 75 namespace

## P3 — DSH Core Compatibility

| รายการ | ค่าจริง |
|---|---|
| เอนจินที่ติดตั้ง | `0.2.1-rc.2` |
| `engines.dsh` ใน package.json | `>=0.2.1-rc.2 <0.3.0` |
| API ที่ใช้ | `addLanguage`, `register`, `setLocale` จาก `ctx.locale` |
| `exports.inject` | `["locale"]` |

ต้องตรวจว่ามี DSH รุ่นใหม่กว่านี้ที่เปลี่ยน API สะพาน locale ไหม — ยังไม่ได้ตรวจ
เพราะไม่มีเครือข่ายยืนยันรุ่นล่าสุดจาก npm (ต้องให้ผู้ใช้ยืนยันก่อนอัปเดต constraint)

## P4 — Translation Coverage เทียบ Source

**สิ่งที่ทำได้**: ตรวจ placeholder mismatch, missing key, obsolete key
ภายในโปรเจกต์เอง (ทำแล้วผ่านหมด)

**สิ่งที่ทำไม่ได้**: เทียบกับ "Source ภาษาอังกฤษของ DSH" ครบชุด เพราะ
แพ็กเกจเอนจินส่วนใหญ่มีแต่พจนานุกรม `zh`/`en` บางตัว และ `locale/*.json`
ของแพ็กเกจเป็น metadata ไม่ใช่พจนานุกรม UI (ยืนยันแล้วรอบก่อน)

**ผลที่ได้รอบก่อน**: จับคู่ namespace กับแพ็กเกจได้ 18 ตัวจาก 75
ที่เหลือต้องไล่จากจุด `register` ในซอร์ส bundel ทีละตัว
